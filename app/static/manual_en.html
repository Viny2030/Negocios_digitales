1. What it is

An API for businesses with three optimization products. Each company has its own key, and its data is kept separate from everyone else's.

ProductWhat it doesWhat you send it
DynamicPricingRecommends a price for each productCost, current price and sales history, on every request
SmartRoutePlans deliveries for a fleetDepot, stops with time windows and vehicles, on every request
LeadMatchAssigns each lead to the best-suited sales repLeads and sales reps; optionally, a history to train your own model

The examples use http://localhost:8000: replace it with the address where the API is installed. The full reference for every field is at /docs.

2. Getting started

Register your company

curl -X POST http://localhost:8000/api/v1/companies \
  -H "Content-Type: application/json" \
  -d '{"name": "Demo Company", "contact_email": "demo@company.com"}'

The response includes the api_key field.

Save the key right away. It is shown only once, because the platform stores just a fingerprint that cannot be turned back into the key.

Use the key

Send it in the X-API-Key header of every request:

curl http://localhost:8000/api/v1/companies/me -H "X-API-Key: YOUR_KEY"

Change the key

If you think it has leaked, generate another one. The old key stops working immediately, so update your systems straight away.

curl -X POST http://localhost:8000/api/v1/companies/me/rotate-key -H "X-API-Key: YOUR_KEY"

Generating a new key requires the current one. If you have lost it, the platform administrator has to step in.

3. How it works

Every request first goes through four controls, in this order. It then follows one of the five lines, depending on the route called.

  • Input
  • Control
  • API route
  • Process
  • Stored data
  • Response

How to read the graph

  • Controls (top row): they stop abuse before resources are spent and check the key. If one fails, the request ends there with an error (see Limits and errors).
  • DynamicPricing and SmartRoute: they calculate everything from the request itself and store nothing.
  • Data upload and Training: these are optional and only serve LeadMatch. The uploaded file feeds the logistic regression, which produces a new version in the model registry.
  • LeadMatch: it uses the company's current model. If there is none yet, it scores with a fallback formula and says so with used_default_scoring: true.

4. What data it handles

The platform stores only company data and what LeadMatch needs. Whatever you send to DynamicPricing, SmartRoute and /lead-match/match is used to respond and then discarded.

How to read the graph

  • Company: only the key's fingerprint (api_key_hash) and its first characters (api_key_prefix), which help you recognize it, are stored.
  • Dataset and CSV file: a company can have several datasets. The table describes each one, and the file lives in the company's own folder.
  • Columns: the model learns from four columns. lead_id and rep_id are accepted in the file but not used for training.
  • Model version and Current version: each training run adds a version, with its metrics and the dataset it used. current.json says which one is in use: a new version only becomes current if it is not worse (see LeadMatch).

5. DynamicPricing

It estimates how demand for each product changes with price and looks for the best price within your rules.

curl -X POST http://localhost:8000/api/v1/dynamic-pricing/price \
  -H "X-API-Key: YOUR_KEY" -H "Content-Type: application/json" \
  -d '{
    "skus": [{
      "sku_id": "sku-1", "base_cost": 100, "current_price": 150, "stock": 50,
      "min_margin_pct": 0.15, "max_daily_variation_pct": 0.10,
      "purchase_events": [
        {"price": 140, "quantity_sold": 30}, {"price": 150, "quantity_sold": 22},
        {"price": 160, "quantity_sold": 15}, {"price": 170, "quantity_sold": 9}
      ]
    }],
    "objective": "margin"
  }'
FieldMeaning
base_cost, current_priceUnit cost and current price. Required.
purchase_eventsPast sales: price and quantity. Estimating demand takes at least 4 events with sales and 2 different prices.
stockUnits available: no more than this is expected to sell. It must refer to the same period as purchase_events. Required.
min_margin_pctMinimum profit on cost. Default: 0.15.
max_daily_variation_pctHow far the price may move from the current one. Default: 0.05.
competitor_price, max_competitor_premium_pctThe competitor's price and how far above it you may sell. Default: up to 0.10 more. Minimum margin and daily variation take priority.
objectivemargin seeks the highest expected profit. volume, the most units sold; if stock runs short, it uses the highest price that still sells everything.

How to read the response

  • recommended_price: the suggested price.
  • used_default_elasticity: if true, there was no data to estimate demand. The current price is kept, adjusted only if it breaks a rule, and expected_quantity and expected_profit come back empty. The price is also kept when there is no stock.
  • expected_margin_on_cost_pct: profit on cost; this is the one to compare with min_margin_pct.
  • expected_margin_pct: profit on price. With a cost of 100 and a price of 115, the first is 15% and this one is 13%.
  • constraints_applied: the rules applied. If they conflict, minimum margin wins, then daily variation, and the competitor last, and this field says so.

6. SmartRoute

It distributes stops among vehicles and sets the order of each trip.

curl -X POST http://localhost:8000/api/v1/smart-route/plan-routes \
  -H "X-API-Key: YOUR_KEY" -H "Content-Type: application/json" \
  -d '{
    "depot": {"lat": -34.6037, "lon": -58.3816},
    "stops": [
      {"stop_id": "s1", "location": {"lat": -34.61, "lon": -58.38}, "demand": 5,
       "time_window_start_min": 0, "time_window_end_min": 240},
      {"stop_id": "s2", "location": {"lat": -34.60, "lon": -58.40}, "demand": 8,
       "time_window_start_min": 0, "time_window_end_min": 240}
    ],
    "vehicles": [{"vehicle_id": "v1", "capacity": 20}]
  }'

Times are expressed in minutes from the start of the shift. Defaults: 5 minutes per stop, 30 km/h and a maximum of 480 minutes per route, including the return to the depot.

How to read the response

  • routes: for each vehicle, its stops in order, with arrival and departure, distance, duration until back at the depot, and load.
  • unassigned_stops: the stops that did not fit in any vehicle because of capacity, schedule or duration. Always check this and handle those stops another way.

7. LeadMatch

It estimates how likely each lead is to buy and assigns it to the sales rep who adds the most, without exceeding anyone's capacity. It works from day one; with your history it can score based on your own results.

Step 1 (optional): upload your history

A .csv, .tsv or .txt file of up to 25 MB. CSV files from Spanish-language Excel are accepted. The columns origin, time_on_site_minutes and company_size describe the lead; converted says whether the lead bought (1/0, yes/no, sí/no or true/false).

curl -X POST http://localhost:8000/api/v1/datasets/lead_match \
  -H "X-API-Key: YOUR_KEY" -F "file=@leads.csv"

Step 2 (optional): train

This takes at least 20 complete rows, with both 0 and 1 cases. Use the id returned by the previous step.

curl -X POST http://localhost:8000/api/v1/lead-match/train \
  -H "X-API-Key: YOUR_KEY" -H "Content-Type: application/json" -d '{"dataset_id": 1}'

The response includes metrics.auc: 0.5 is the same as scoring at random, and the closer to 1, the better.

Training does not always change the model in use. The new version is saved, but it only becomes current if its AUC reaches 0.55 and it is no worse than the current model measured on the same rows. Check promoted and promotion_reason in the response.

Step 3: assign

curl -X POST http://localhost:8000/api/v1/lead-match/match \
  -H "X-API-Key: YOUR_KEY" -H "Content-Type: application/json" \
  -d '{
    "leads": [{"lead_id": "l1", "origin": "paid_ads", "time_on_site_minutes": 22, "company_size": 300}],
    "reps": [{"rep_id": "r1", "capacity": 2}, {"rep_id": "r2", "capacity": 3, "specialties": ["paid_ads"]}]
  }'

For each rep you can set historical_close_rate (default: 0.5) and specialties, which multiply the score by specialty_bonus (default: 1.2).

How to read the response

  • assignments: lead, sales rep, purchase probability and score.
  • unmatched_leads: leads with no rep because of insufficient capacity.
  • used_default_scoring: true means the fallback formula was used instead of your own model.

View versions and return to an earlier one

To list the versions, with their metrics and which one is current:

curl http://localhost:8000/api/v1/lead-match/models -H "X-API-Key: YOUR_KEY"

To make a version current, whether an earlier one or one that training did not promote:

curl -X POST http://localhost:8000/api/v1/lead-match/models/{version_id}/promote -H "X-API-Key: YOUR_KEY"

10. Current limitations

These are worth knowing before you use the results in a real decision.

DynamicPricing

  • It estimates demand from price alone: it does not consider seasonality, promotions or market changes. With few events, the estimate is weak.
  • The competitor only acts as a ceiling: it does not push the price down if you are already below that limit.

SmartRoute

  • It calculates in straight lines at constant speed, with no streets or traffic: real times will be longer, so leave some slack in your time windows.
  • It looks for a good solution, not necessarily the best possible one. A stop listed as unassigned might fit with a different distribution of routes.
  • All routes leave the depot at the start of the shift, and there is a single depot.

LeadMatch

  • The model uses only three lead attributes: origin, time on site and company size. It does not learn from each rep's history: you supply the close rate and specialties.
  • Promoting a version does not prove it will work well on future leads: AUC is measured on historical data.

Account

  • Sign-up does not verify the email, and the 409 error reveals whether an email is already registered.

11. Installation

For whoever installs the platform. Requires Python 3.11.

pip install -r requirements.txt
cp .env.example .env
alembic upgrade head
uvicorn app.main:app
  • Existing database: back it up and run alembic upgrade head before starting the new version. Keys already issued keep working, but that migration cannot be reverted.
  • Behind a proxy or PaaS: set TRUSTED_PROXY_HOPS (see .env.example). Otherwise, all clients share the per-IP limits.
  • Files: datasets and models are stored in storage/. On a PaaS, mount a persistent volume there or they will be lost on redeploy.
  • Multiple instances: limit counters live in each process's memory. Sharing them requires common storage such as Redis.
